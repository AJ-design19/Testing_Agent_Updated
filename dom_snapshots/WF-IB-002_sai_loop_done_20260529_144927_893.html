1. Project Overview

1.1 Problem Statement

Launching new products without a validated audience leads to wasted effort and missed momentum.

  • Current Pain Point: Founders and product teams lack a streamlined way to capture early interest, build pre-launch buzz, and incentivize organic growth before a product goes live.
  • Impact: Without a viral waitlist mechanism, teams resort to expensive paid acquisition or launch to silence — missing the opportunity to build community-driven demand.
  • Root Cause: Most waitlist tools are either too simple (just an email form) or too expensive, lacking built-in viral mechanics that turn each signup into a growth engine.

1.2 Solution Overview

  • Proposed Solution: A self-contained waitlist web application with email capture, a viral referral loop (unique referral links that reward referrers with queue advancement), real-time position tracking, and a full admin panel for managing signups and analytics.
  • Key Differentiators:
    • Built-in viral referral mechanics — each signup generates a unique shareable link
    • Gamified position advancement — referrers move up the queue, creating urgency
    • Real-time position reveal — users see their rank and referral impact instantly
    • Full admin control — approve, remove, export, and configure the waitlist without engineering involvement

1.3 Business Justification

  • Business Value: Enables product teams to validate demand, build an engaged audience, and generate organic growth before launch — all at near-zero acquisition cost.
  • Expected ROI: A viral coefficient > 1.0 means each signup generates more than one additional signup, creating exponential growth without proportional marketing spend.
  • Risk of Not Doing: Launching without a pre-built audience leads to low initial adoption, higher customer acquisition costs, and missed word-of-mouth momentum.

3.2 Key User Journeys

  1. New User Signup Journey

    • Trigger: User lands on the waitlist page (from direct URL, social media, or ad)
    • Steps:
      1. User sees compelling headline and value proposition
      2. User enters email (and optionally, name)
      3. System validates email and checks for duplicates
      4. System assigns queue position and generates unique referral link
      5. User sees confirmation with their position, referral link, and sharing options
    • Expected Outcome: User is successfully registered and immediately presented with sharing incentives

  2. Referral Sharing Journey

    • Trigger: User views their referral link on the confirmation/status page
    • Steps:
      1. User copies or clicks social share buttons for their unique referral link
      2. User shares link via Twitter, LinkedIn, email, WhatsApp, or direct message
      3. New user clicks the referral link and lands on the signup page (with referral tracking)
      4. New user signs up → referrer is credited
      5. Referrer's position advances; they receive updated position info
    • Expected Outcome: Referrer moves up in the queue; new user joins successfully

  3. Position Check Journey

    • Trigger: User wants to check their current waitlist status
    • Steps:
      1. User visits the status page (via bookmarked link or email link)
      2. User enters their email or uses a unique status URL
      3. System displays: current position, total waitlist size, referral count, positions gained
    • Expected Outcome: User sees their live position and is motivated to share more

  4. Admin Management Journey

    • Trigger: Admin needs to review or manage the waitlist
    • Steps:
      1. Admin logs into the protected admin dashboard
      2. Admin views signup list with search/filter capabilities
      3. Admin performs actions: approve, remove, export CSV, view analytics
      4. Admin adjusts settings (referral reward amount, open/close signups)
    • Expected Outcome: Admin has full visibility and control over the waitlist

3.3 Pain Points Addressed

  • "I signed up but have no idea what's happening": Position reveal and confirmation UI provide instant transparency
  • "There's no reason for me to tell others": Referral rewards (queue advancement) create a strong, gamified incentive
  • "I can't manage this without engineering help": Full admin panel enables self-service management
  • "Spam and fake signups are polluting the list": Rate limiting, honeypot fields, and email validation protect data integrity

5.2 Viral Referral Loop

FR-03: Unique Referral Link Generation [Must Have]

FR-04: Referral Tracking & Position Advancement [Must Have]

  • Description: When a new user signs up via a referral link, the referrer is credited and their queue position advances.
  • Inputs: New signup with a valid referral code in the URL

    • Position cannot go below #1 (capped at top)

    • A user can only be referred by one referrer (first referral link wins)
  • Acceptance Criteria:
    • Referrer's position decreases by the configured reward amount upon successful referral
    • Referral count on referrer's profile increments correctly
    • Position never goes below 1
    • Invalid or self-referrals are rejected silently
    • Referral chain is stored (referrer → referred relationship)

8. Referral Mechanics — Detailed Specification

8.1 Position Calculation Logic

  • Initial Position: Assigned sequentially at signup time (nth signup = position n)
  • On Referral Event: Referrer's position decreases by referral_reward (default: 3)
    • If current position is 50 and reward is 3 → new position is 47
    • All users between position 47–49 shift down by 1 position
  • Position Floor: Minimum position is always 1 (cannot go negative or zero)
  • No Backward Movement: Users never lose positions due to others' referrals (only the referrer moves up; displaced users shift down by 1)

8.2 Referral Code Format

  • Format: 8-character alphanumeric string (e.g., a7Bk92mX)
  • Uniqueness: Generated using a collision-resistant method (nanoid or UUID prefix)
  • URL Format: https://<domain>/?ref=<code>

8.3 Anti-Gaming Rules

  • Self-referral prevention: same email cannot use own referral code
  • Duplicate email prevention: each email can only sign up once
  • Rate limiting prevents mass bot signups through a single referral link
  • Honeypot field catches automated form submissions
